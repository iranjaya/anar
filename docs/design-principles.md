# Anar design principles

Worth adopting much from Aragon, especially feature ownership, reuse by product meaning, and clear UI states.

Key takeaways for [the UI mock spec](specs/ui-mock-slice.md). Section and U-slice references below identify where to apply them; they do not change that spec themselves. Aragon's detailed platform design pages are marked draft. The stricter module boundaries below are recommendations for Anar, not claims that Aragon enforces them everywhere.

## Module ownership and dependencies

| Takeaway | Aragon reference and what Anar should take | Spec impact |
| --- | --- | --- |
| 1. A feature owns its UI and behavior | Aragon's [project structure](../../aragon/app/apps/app/docs/projectDocs/projectStructure.md) puts pages, components, services, utilities and tests inside modules; [the root route](../../aragon/app/apps/app/src/app/page.tsx) only exports a module page. Adopt this ownership: `leads` owns Today, detail and assignment UI; `followups` owns call logging; `imports` owns mapping and import steps; `reports` owns dashboard composition. Keep route files thin. Add subfolders only when needed. | §4; U2, U4–U10 |
| 2. Expose a deliberate public surface | The [ENS module](../../aragon/app/apps/app/src/modules/ens/index.ts) exposes selected hooks, types and configuration. Adapt: document each Anar module's public functions, types and reusable components. Keep server queries, server actions and client components in separate entry points so importing UI cannot pull in the mock store or future database code. Avoid a barrel that exports everything. | §§2, 4–5; U0–U3 |
| 3. Compose features through their owners | Aragon's [dashboard composition](../../aragon/app/apps/app/src/modules/dashboard/components/dashboardOnboarded/dashboardOnboarded.tsx) imports finance and governance components directly. Adopt composition, with tighter boundaries: the dashboard imports `AssignList` from `modules/leads`, never from another route's `_components`. Shared primitives must not import feature modules; feature dependencies must be explicit and acyclic. A module owns writes to its feature's state. | §§2, 4; U9–U10 |
| 4. Share meaning, not just appearance | [Platform principle 7](../../aragon/strategy-doc/platform-doc/internal/design/principles.md) generalizes around the same product meaning; the [UI kit](../../aragon/app/packages/gov-ui-kit/AGENTS.md) separates primitives from domain composition. Adopt: generic Sheet, Chip and layout primitives stay shared; `ScoreBadge` belongs to scoring, `CallButton` to leads, and import steps to imports. Being used on two screens does not make a component generic. | §§4, 7; U3, U5, U7 |
| 5. Make names predictable | Aragon's [naming conventions](../../aragon/app/apps/app/docs/codingGuidelines/namingConventions.md) use PascalCase component names, a `Page` suffix and `on…` callbacks. Adopt those conventions while keeping Anar's existing PascalCase component filenames and camelCase functions. Keep the spec's product names and function contracts, such as `Lead`, `logFollowUp` and `assignLeads`; avoid competing names for the same concept. | §§4–5; U0–U3 |
| 6. Keep data access behind the module seam | Aragon's [data fetching guide](../../aragon/app/apps/app/docs/projectDocs/dataFetching.md) separates service requests from presentation. Adopt the separation with Anar's existing server queries and actions. Only server-side module implementations import `mock/**`; components consume results or invoke actions. Make future I/O functions asynchronous from the start so replacing mocks with Postgres does not change callers. | §§2, 5–6; U1–U2, U4–U10 |

## Interface behavior

| Takeaway | Aragon reference and what Anar should take | Spec impact |
| --- | --- | --- |
| 7. Show the useful summary and its evidence | [Honest abstraction](../../aragon/strategy-doc/platform-doc/internal/design/principles/honest-abstraction.md) pairs a readable model with inspectable detail. Adopt: keep Why Hot, timeline entries and links to affected import rows. Label dashboard periods beside their values: the range selector changes the team table and comparison, while tiles retain their own periods. | §§5–7; U5, U8, U10 |
| 8. Every element must answer a current question | [Every element makes a claim](../../aragon/strategy-doc/platform-doc/internal/design/principles/every-element-makes-a-claim.md) requires controls, labels and empty states to earn their place. Adopt: keep unfinished routes out of navigation, omit empty lead fields, and distinguish no leads, no matching results and a failed load. Never turn a request failure into zero counts or a Good day card. | §§3, 6–7; U4–U5, U9–U10 |
| 9. Availability communicates; authorization enforces | [Control availability](../../aragon/strategy-doc/platform-doc/internal/design/control-availability.md) distinguishes hidden, disabled, guarded and consequential actions. Adopt the distinction: hide manager-only controls from Admins; explain unavailable Call beside an invalid phone; explain what is missing when Save is disabled. Server functions still check company, role and ownership. | §§2–3, 6; U2, U5–U6, U9 |
| 10. Give each decision one lead action | [Primary action hierarchy](../../aragon/strategy-doc/platform-doc/internal/design/primary-action-hierarchy.md) allows at most one primary action per decision context. Adopt: Call leads on a lead row, Save in the call sheet, Check rows before review, Import at commitment. Alternatives stay secondary; labels name the immediate outcome. | §§6–7; U3, U6–U9 |
| 11. Preserve input and make repair local | [Validation timing](../../aragon/strategy-doc/platform-doc/internal/design/validation-timing.md) and [dialog continuity](../../aragon/strategy-doc/platform-doc/internal/design/dialog-continuity.md) preserve the task while correcting errors or making smaller decisions. Adopt: no errors on untouched fields; show blocking errors at the relevant field or step; keep mapping selections when going back and call details after a failed save. Keep one owner for each form's state. | §6; U6–U8, U10 |
| 12. Make consistency and behavior verifiable | The [UI kit rules](../../aragon/app/packages/gov-ui-kit/AGENTS.md) require token-backed styling and accessible composition; [testing guidance](../../aragon/app/apps/app/docs/projectDocs/testing.md) tests the subject's behavior through roles, labels and text. Adopt with Anar's tokens, native controls, shadcn Sheet, Vitest and Playwright. Add proofs for input preservation, disabled explanations and failed-versus-empty states alongside the existing 390 px and role-flow checks. | §§7, 10; U0, U3–U11 |

## What Anar should not copy

- **Monorepo and publishing machinery:** Turbo, workspace catalogs, independent release trains and a published UI package serve Aragon's multiple consumers. Keep Anar one app with local components ([root conventions](../../aragon/app/AGENTS.md)).
- **Plugin and domain frameworks:** Aragon's [slot registry](../../aragon/app/apps/app/docs/projectDocs/pluginEncapsulation.md) and [DDD package](../../aragon/app/packages/aragon-domain/AGENTS.md) solve governance variation and a separate domain API. Keep Anar's company differences in schema and scoring configuration, with specialized code owned locally when needed. No slot registry, service-class hierarchy or domain package for the mock slice.
- **The exact runtime and test setup:** Aragon uses React Query hydration, React Hook Form wizards, wallet tooling and live-DAO E2E tests ([data fetching](../../aragon/app/apps/app/docs/projectDocs/dataFetching.md), [forms](../../aragon/app/apps/app/docs/projectDocs/formsAndWizards.md), [E2E](../../aragon/app/apps/app/e2e/README.md)). Keep Anar's server actions, simple form state, fixed mock seed and phone/desktop Playwright projects. Do not copy its assistant-pane breakpoint overrides or governance-specific control rules.

Count: 12 takeaways to adopt or adapt; 3 groups to leave out.
